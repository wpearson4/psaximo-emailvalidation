# Validation technique assessment

The strongest current techniques are stage-aware SMTP interpretation, explicit abstention, and differential recipient behavior. The largest remaining risks occur when one layer loses the uncertainty or freshness recorded by another. “Valid” in this platform is a technical evidence classification; it is not proof of inbox placement, future delivery, or user ownership.

## DNS uncertainty is lost across layers

**Reproduced, EV01.** `EmailClassificationEngine.Classify` correctly returns Unknown for DNS timeout/failure. `ResultEvaluator.AddRouting` independently treats `!MxPresent` as NoMailRouting without checking DNS success. `EmailValidator` merges these reasons. `RevalidationPolicy.TerminalReasons` contains NoMailRouting, so retry is denied. The offline composition produced `DnsTimeout,NoMailRouting`, NoMailRouting detail, and `ShouldRetry=false`. `ValidationEvidenceAssessment.Quality` also calls missing MX conclusive before checking transient DNS.

Evidence: [ResultEvaluator.cs · private static void AddRouting](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Core/ResultEvaluator.cs:77), [EmailValidator.cs · ReasonCodes = classification.ReasonCodes](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Core/EmailValidator.cs:282), [RevalidationServices.cs · private static readonly HashSet<ReasonCode> TerminalReasons](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Core/RevalidationServices.cs:63), [ValidationEvidenceAssessment.cs · public static EvidenceQuality Quality](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Core/ValidationEvidenceAssessment.cs:9).

Separately, `MxDnsResolver` catches every SocketException from implicit address lookup and returns successful DNS with no route. A temporary address-resolution failure can therefore become Invalid/NoMailExchanger. This path is source-verified, not exercised against live DNS. Only authoritative no-address evidence should support no-route invalidity; SERVFAIL, transport failures and resolver outages should retain uncertainty.

The wire client reads flags before verifying minimum response length, ignores UDP sender identity, and does not comprehensively validate QR/opcode/question/record owner/class. It detects any root exchange as Null MX, without requiring preference zero and a sole MX record. The synthetic mixed ordinary/Null MX response returned ExplicitNullMx=true. RFC 7505 defines the sole zero-preference root record; mixed records are a configuration conflict, not clean proof of no mail service. [RFC 7505 section 3](https://www.rfc-editor.org/rfc/rfc7505.html#section-3). Prefer a well-tested open-source DNS implementation or consolidate the repository’s duplicate parsers behind one tested wire contract; no recurring service is necessary.

## Freshness must belong to individual observations

**Reproduced, EV02.** `DomainLifetime` ignores DNS result category, imposes a five-minute minimum, and treats zero/missing TTL as the 24-hour configured fallback. NXDOMAIN/SERVFAIL have no parsed negative TTL here. The synthetic calls produced 24 hours for missing and zero TTL, and five minutes for a 30-second TTL. Negative answers need their own resolver evidence and expiration; RFC 2308 defines negative caching using SOA information. [RFC 2308](https://www.rfc-editor.org/rfc/rfc2308.html).

`PersistentDomainValidationCache.StoreAsync` always resets EvidenceExpiresAt to now plus lifetime. Both `RefreshCatchAllAsync` and `UpdateRecipientBehaviorAsync` call it using the routing TTL even though DNS was not refreshed. The synthetic cache call extended an expiry by 3,540 seconds. This can keep old routing evidence current on paper while domain behavior evolves. [DomainIntelligenceServices.cs · private TimeSpan DomainLifetime](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Application/DomainIntelligenceServices.cs:462), [JsonValidationIntelligenceStore.cs · public async Task StoreAsync](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Infrastructure/JsonValidationIntelligenceStore.cs:381).

Use separately immutable observed/expiry times for routing, recipient behavior, provider, authentication and risk. Refreshing one must not renew another. Preserve stale evidence as historical context with an explicit age/quality downgrade, not current truth. Domain-level expiration should be derived from the component needed for the next decision.

## SMTP protocol and recipient interpretation

The probe connects to port 25 with a selected local identity, records greeting/EHLO/HELO, checks SMTPUTF8, sends MAIL FROM and RCPT, then RSET/QUIT. It never sends DATA. Per-command and connection timeouts are ten seconds by default; per-address session budget is eight; up to three MX hosts may be consulted. Every control and target probe creates a separate connection. Stable sender/IP selection and throttle/reputation checks are strengths; observed restrictions should continue to stop or defer work, never trigger evasion.

**Verified gap, EV05.** EHLO STARTTLS is only detected; no STARTTLS command, TLS stream, certificate validation or post-TLS EHLO exists. Google’s documented 4.7.x responses include both TLS requirements and several other restrictions, so treating that family uniformly as rate limiting loses cause information. Implement ordinary authenticated TLS negotiation with explicit TLS-required/failure states and bounded timeouts. Do not interpret TLS failure as mailbox invalidity. [SmtpMailboxProbe.cs · tlsAdvertised = ehlo.Text.Contains](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Infrastructure/SmtpMailboxProbe.cs:231), [Google SMTP errors](https://knowledge.workspace.google.com/admin/support/troubleshooting/gmail-smtp-errors-and-codes), [RFC 3207](https://www.rfc-editor.org/rfc/rfc3207.html).

**Reproduced protocol risk.** `ReadResponseAsync` retains the first reply code but accepts different codes in subsequent lines, arbitrary terminal separators, and unbounded line count/length. The synthetic transcript beginning `250-` and ending `550 5.1.1` parsed as code 250. Candidate enforced classification examines 2xx before rejection text; such malformed input can consequently be interpreted as acceptance if sufficient session provenance is present. Reject inconsistent/oversized responses as ProtocolFailure and bound total session/cleanup duration. [SmtpMailboxProbe.cs · private static async Task<SmtpResponse> ReadResponseAsync](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Infrastructure/SmtpMailboxProbe.cs:363).

Reply handling has two live implementations: legacy canonical text-first classification and candidate structured/provider rules. Default Shadow preserves the legacy outcome. The candidate constrains permanent recipient labels when the primary reply is 4xx; the legacy path can assign a recipient-rejection category from wording before reply class, although session policy prevents a 4xx from becoming strong permanent rejection. Preserve this protection and resolve candidate/canonical disagreements through fixtures and shadow evidence, not a blind mode switch. [SmtpResponseClassifier.cs · private static SmtpResponseCategory ClassifyCategory](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Infrastructure/SmtpResponseClassifier.cs:99), [SmtpResponseClassifier.cs · private static SmtpResponseRuleRegistry.RuleMatch? ConstrainByReplyClass](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Infrastructure/SmtpResponseClassifier.cs:188).

Acceptance is generally handled conservatively. Generic/Microsoft Valid requires accepted target plus strong negative catch-all evidence. Gateway acceptance without discrimination is Unknown. MailboxFull is Risky and should describe a reported capacity condition, not assert confirmed ownership. A timeout, disconnect, provider block or source-IP restriction remains inconclusive. Neither accepted RCPT nor full-mailbox text guarantees actual future delivery.

Microsoft documents DBEB rejection of unknown recipients, including its 550/5.4.1 form; that supports the narrow existing rule but not universal mailbox certainty across all EOP domains. Yahoo distinguishes temporary 421/451 failures from permanent errors and policy causes. [Microsoft DBEB](https://learn.microsoft.com/en-us/exchange/mail-flow-best-practices/use-directory-based-edge-blocking), [Yahoo SMTP errors](https://senders.yahooinc.com/smtp-error-codes/).

A configurable capability model should extend `ProviderPolicyResolver`: recipient discrimination reliability, control permission/utility, accepted-response interpretation, SMTPUTF8/TLS expectations, permitted concurrency, retryable causes and minimum intervals. Keep evidence-dependent classification in tested code. Version profiles; review unknown-response and shadow-disagreement trends; use a canary with rollback. Do not automatically learn that “all accepted means valid.”

## Catch-all detection in detail

The current detector uses cryptographically random `dwcheck-` local parts. With default ProbeCount=1 and MinimumAcceptedProbes=2, unanimous acceptance/rejection normally causes two probes; mixed classes stop early. Explicit recipient rejection requires MAIL FROM success and a 5xx RCPT rejection. Temporary/control ambiguity remains Unknown. One accepted observation is only a candidate.

`DomainRecipientBehaviorPolicy.Evaluate` requires accepted target and controls on the same MX, within a five-minute correlation window, with no MX conflict. Confirmation requires two independent observation sessions at least fifteen minutes apart by default. Topology filtering precedes aggregation. Contradictions reset confirmation; persisted legacy evidence is normalized conservatively. Protected observation arrays preserve controls and qualified rejections separately from ordinary traffic. These are strong safeguards.

**Verified limitations, EV08 and EV09.** Controls run only on the selected first MX, but a RecipientSpecific domain state can raise acceptance strength for another consulted MX. The accept-all path has explicit endpoint correlation; the negative-control path lacks equivalent target-MX binding. Controls rejected solely because their shared local-part pattern appears synthetic would also produce recipient-specific confidence without proving the target exists. These are plausible false-valid mechanisms; their frequency is unmeasured. Conversely, a real catch-all may stay Unknown after greylisting, blocks, time-window misses or budget exhaustion. That abstention is preferable to fabricated certainty.

Fresh confirmed accept-all is **not** covered by `UsePersistedCatchAll`, which requires independent catch-all routing evidence. The offline planner still requested a target probe for confirmed accept-all. Different addresses at the same endpoint can thus repeat low-value probes even though the classifier explains why another acceptance cannot resolve the mailbox. Add an explicit non-discriminating reuse plan returning Unknown/Inconclusive, with a bounded domain refresh schedule and a way for authorized contradictory evidence to invalidate it. Do not turn it into Valid or skip targeted investigation when genuinely new evidence could change the result.

Independent catch-all routing is representable, but no production acquisition path assigning `IndependentRoutingEvidence` was found in the source. The reusable confirmed-catch-all branch is therefore a capability for injected/persisted authoritative evidence, not something the SMTP detector can establish itself. Add authenticated operator/domain-owner evidence ingestion if this distinction has customer value; store source, scope, timestamp, expiry and revocation.

Use endpoint-scoped recipient-specific evidence with freshness and provider versions. Keep the taxonomy explicit: candidate acceptance, confirmed public accept-all, recipient-specific rejection observed, independently confirmed catch-all routing, provider-restricted and unknown. Restriction can be an orthogonal verification state. No active delivery experiment or probe expansion should occur without authorization.

## Retry usefulness and resilience

**Reproduced, EV03.** Under defaults the schedule policy chooses five seconds for a temporary failure, while result reuse allows two minutes. A synthetic temporary mailbox record was reusable at retry time with 115 seconds remaining. The processor calls the normal service and records reused executions; it lacks a new-evidence requirement. A reused Completed disposition may still carry original ProbeAttempted=true, so the special local-cooldown reschedule path does not solve this.

Request `evidenceObservedAfter` for a durable retry and require fresh evidence in the unresolved layer. Schedule greylisting in provider-appropriate windows with positive jitter, preserve sender identity, and distinguish policy restrictions from likely recoverable transport failures. Time or infrastructure retries should not exhaust an observation budget. Stable verification restrictions should finalize as Inconclusive after bounded investigation, or await configuration/evidence change.

**Source-backed distributed risks, EV04.** A second receiver that finds LifecycleState=Revalidating skips the initial CAS transition and can call the validation service concurrently. Process-local single flight does not protect separate hosts. Overdue recovery only handles RetryWaiting, not abandoned Revalidating ownership. Also, deferral changes ScheduledRetryAt while keeping `validationId:attempt` MessageId. If duplicate detection is enabled and the replacement falls in the broker window, it can be discarded. Azure explicitly includes scheduled messages in duplicate detection. [Azure duplicate detection](https://learn.microsoft.com/en-us/azure/service-bus-messaging/duplicate-detection). Use a fenced expiring execution lease and a persisted dispatch generation; retries of the same dispatch retain its ID, while intentional reschedules get a new ID.

## Historical state and scale

`MongoValidationIntelligenceStore.SaveDomainAsync` updates by domain ID without an expected version or observation-time condition. The application’s read-before-write comparison cannot prevent another process from committing newer evidence between those operations. A slow result can overwrite a newer topology/recipient-behavior decision. Add versioned conditional writes and merge immutable observations.

The Mongo mailbox cache is an unbounded dictionary and can serve old values after another worker updates Mongo; the reuse policy limits classification lifetime but cannot discover a newer contradictory record through that dictionary. Domain cache has no size bound. `InMemoryValidationResultCache` bounds active entries but its insertion-token queue grows on repeated replacement/removal while the entry count stays below the limit. These increase memory/cross-host consistency risk on large datasets. Measure and bound both entry and bookkeeping retention.

General historical reliability is a hand-weighted ratio over retained observations, not calibrated success probability. It lacks a general age window and provider-strategy-version filter. Add time decay or explicit windows, denominators, missingness, and independent sample counts. Preserve topology changes and route-level differences; avoid treating high traffic as independent corroboration.

## Confidence and public semantics

The deterministic classifier uses fixed weights and branch scores: these are heuristic confidence in a conclusion, not calibrated probabilities. A DNS timeout can have a numerical score of 0.88 while the qualitative level is Low. The REST DTO exposes Confidence but omits ConfidenceType and model provenance. This is especially problematic if model enforcement later switches the meaning of the number.

Keep backward-compatible detailed statuses and add a stable customer summary: Valid, Invalid, Risky, Inconclusive. Map LikelyValid conservatively to Risky with a “likely valid” detail unless a documented product policy says otherwise; map LikelyInvalid to Risky with suspected invalidity rather than definitive Invalid; CatchAll to Risky; Unknown to Inconclusive. Keep evidence confidence High/Medium/Low independent from mailing risk and Final/Provisional. Final Inconclusive means no further automatic work is planned, not mailbox invalidity.

Publish score type, named target, evidence timestamps, policy versions and model/calibration version. Continue heuristic scoring as an explanation if compatible clients need it; do not present fixed weights as percentages of delivery. Calibrate separate outcomes for mailbox existence, delivery within a defined window, and hard bounce, with temporal/domain holdouts and confidence intervals. Preserve explicit deterministic evidence and provider restrictions.

## Authentication and supplemental risk

SPF concerns authorization of a sending host; DKIM concerns signed message content and a selector-based key. Neither establishes the existence of an individual recipient. The active deterministic mailbox classifier does not treat their presence as proof. [SPF specification](https://www.rfc-editor.org/rfc/rfc7208.html), [DKIM specification](https://www.rfc-editor.org/rfc/rfc6376.html).

Authentication parsing currently participates in domain fingerprint changes, and missing authentication/DNSSEC fields participate in prediction support checks even though the logistic encoder does not encode those fields. Missing optional security enrichment should not by itself manufacture mailbox invalidity or unnecessary SMTP work. Align support checks with the actual model feature schema.

Role/disposable/trap/suppression flags mostly remain independent of technical status. Preserve that separation. Do not silently apply typo suggestions or claim that a configured/heuristic trap flag is authoritative. Return Unknown for age/alias/identity where unavailable. Add governed dataset refresh and a current suppression overlay on every returned result; hot memory reuse currently bypasses `EnrichAsync`.
