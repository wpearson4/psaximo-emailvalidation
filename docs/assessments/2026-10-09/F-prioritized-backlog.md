# Prioritized implementation backlog

These items are ready for implementation planning, not authorization to modify production code in this assessment. Priorities refer to the assessed baseline. Each item includes a testable behavior change and references the affected implementation. Complexity estimates use the scale in [ranked opportunities](D-accuracy-opportunities.md).

## EV01 Preserve transient DNS outcomes through classification

**Priority:** P1. **Problem:** Resolver uncertainty can become no-route invalidity or suppress recovery. **Existing behavior:** `AddRouting` adds NoMailRouting for empty MX even on timeout; implicit A/AAAA fallback swallows every SocketException. **Proposed behavior:** Only authoritative NXDOMAIN, valid Null MX or definitive no-route evidence may support permanent invalidity; all transient DNS states remain Inconclusive and retry-eligible.

**Business value:** Avoid lost valid addresses and pointless final failures during outages. **Technical approach:** Introduce typed routing outcomes; make evaluator, evidence quality, risk and retry consume the same outcome. Distinguish HostNotFound/NoData from temporary resolver errors. Validate DNS packets and mixed Null MX before emitting definitive facts. [MxDnsResolver.cs · public async Task<DnsLookupResult> ResolveAsync](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Infrastructure/MxDnsResolver.cs:17), [ResultEvaluator.cs · private static void AddRouting](/Users/wpearson4/projects/EmailValidation/src/EmailValidation.Core/ResultEvaluator.cs:77).

**Acceptance criteria:** Timeout/SERVFAIL cannot emit NoMailRouting, conclusive routing evidence or Invalid; an enabled retry is scheduled; authoritative absent routing still becomes Invalid; short/mismatched DNS responses return structured failure. **Complexity:** M. **Dependencies:** None; coordinate with EV02. **Validation:** Synthetic full-pipeline DNS matrix, malformed packets, resolver exception injection, existing routing regressions; no public probes.

## EV02 Separate observation expiry from cache storage time

**Priority:** P1. **Problem:** Cached evidence can outlive its authority. **Existing behavior:** Missing/zero TTL becomes 24 hours; TTL below five minutes is extended; catch-all writes reset domain expiry. **Proposed behavior:** Each evidence component expires from its original observation; transient failure has a short retry horizon and never renews good facts.

**Business value:** Detect routing changes and recover promptly without unnecessary repeated SMTP. **Technical approach:** Add routing/behavior/provider/authentication clocks; preserve absolute expiry in cache writes; handle zero TTL as immediately stale; parse authoritative negative TTL; inject TimeProvider throughout. Migrate old records conservatively. **Acceptance criteria:** Behavior updates never extend routing expiry; zero/30-second TTLs are not inflated; transient DNS does not remain fresh for a day; topology refresh invalidates dependent controls; historical timestamps survive reuse. **Complexity:** M. **Dependencies:** EV01 outcome types. **Validation:** Fake-clock sequences spanning DNS failure/recovery, candidate confirmation, topology change and persisted-cache reload.

## EV03 Require useful fresh evidence on durable retries

**Priority:** P1. **Problem:** Retry budgets can expire without new evidence. **Existing behavior:** Default five-second backoff is shorter than two-minute transient reuse; retry uses normal cached validation service. **Proposed behavior:** A scheduled observation retry cannot complete using evidence from before its preceding attempt.

**Business value:** Higher useful retry yield and fewer queue/storage operations. **Technical approach:** Add retry intent/evidence-after timestamp; planner refreshes only unresolved layers; preserve cooldowns and unchanged DNS that is genuinely fresh. Count new observation attempts separately from dispatch/infrastructure retries. Use provider/cause-specific intervals with positive jitter. **Acceptance criteria:** The reproduced five-second/two-minute case obtains new eligible evidence or reschedules without consuming an attempt; greylist/block cooldowns cannot be bypassed; maximum observation budget remains enforced; mailbox-full and provider restrictions have explicit policies. **Complexity:** M. **Dependencies:** EV01/EV02. **Validation:** Fake-clock tests through actual service/coordinator chain, reuse hits during retries, long cooldowns, expiry and exhausted outcomes.

## EV04 Fence retry execution and version broker dispatches

**Priority:** P1. **Problem:** Concurrent redelivery can repeat SMTP and broker deduplication can drop a valid reschedule. **Existing behavior:** Already-Revalidating skips acquisition; deferred messages retain the same MessageId; recovery only reconstructs RetryWaiting. **Proposed behavior:** One unexpired owner executes an attempt, while every intentional reschedule has durable distinct dispatch identity.

**Business value:** Predictable finality, lower duplicate traffic, safe restart recovery. **Technical approach:** Mongo CAS lease owner/expiry/fencing token; renew during work; require token at result commit. Persist DispatchGeneration and include it in broker MessageId; repeat publication of one generation keeps the same ID. Recover abandoned execution and use indexed eligible-state queries. ## EV06 Use one mailbox identity and transport syntax policy

**Business value:** Avoid cross-mailbox contamination and invalid input traffic. **Technical approach:** Versioned MailboxKey service reused by cache, single flight, persistence, lifecycle and correlations; count UTF-8 octets; define quoted-local/address-literal product support.
